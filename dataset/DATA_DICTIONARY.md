# Dataset Documentation

Generated by `generate_dataset.py`. Every column is also in
`data_dictionary.csv`, so a script can select features by role rather than by
a hand-maintained list:

```python
import pandas as pd
d = pd.read_csv('data_dictionary.csv')
features = d[d.role == 'feature'].column.unique()
```

## Files

| File | Rows | What it holds |
|---|---|---|
| `query_features.csv` | 180 | one row per query instance|
| `plan_features.csv` | 4836 | one row per candidate plan  |
| `template_dataset.csv` | 4836 | the two joined, ready for training |
| `instance_provenance.csv` | 180 | how each instance was generated — not features |
| `data_dictionary.csv` | — | this document, machine readable |
| `template_dataset.xlsx` | — | all of the above as worksheets |

In `template_dataset.csv` a column appearing in both tables is suffixed:
`n_joins_plan` is the number of join operations in the physical plan,
`n_joins_query` the number of joins in the normal form. They differ when a plan
introduces or removes operations.

## Roles

Every column has one of four roles.

- **id** — identifiers. Never train on these.
- **feature** — inputs to the model.
- **target** — what you predict. Never use one target as a feature for another.
- **metadata** — for reading and analysis, not for training.

## Query features (from the normal form)

These come from `N(Q)`, so every instance of a query has identical structural
values. That is the property the framework depends on.

### Structural — read off the normalised expression

| Column | Meaning |
|---|---|
| `n_terms` | Terms in the union of the normal form. 1 unless the query has a union or a disjunctive selection split by rule u6. |
| `n_rel` | Distinct base relations referenced. |
| `n_joins` | Inner joins. |
| `n_anti` | Anti-joins and semi-joins, from `EXCEPT`, `NOT EXISTS` and `NOT IN` after rule t2 and the `EXISTS` translation. |
| `n_sel` | Selection predicates over base attributes. |
| `n_agg` | Aggregate functions. |
| `n_group` | Grouping attributes. |
| `n_sort` | Ordering attributes. |
| `depth` | Nesting depth of normalised subexpressions. 1 for a flat query; 2 when a join operand or an anti-join operand is itself a normal form. |

### Statistical — read from the catalogue

| Column | Meaning |
|---|---|
| `size_class_max` | Size class of the largest input: `small` (≤200 MB), `medium` (≤2000 MB), `large`. Categorical — encode it. |
| `n_large` | Input relations over 2000 MB. |
| `n_small` | Input relations at or under 200 MB. Small relations fit in transient memory, which is what makes a nested-loop join viable. |
| `tier_min` | Fastest tier holding any input, 0–3. |
| `tier_max` | Slowest tier holding any input, 0–3. |
| `input_mb` | Total size of all inputs, MB. |

## Plan features (from the physical plan)

Plans are not normalised: the differences between candidates are what the
framework selects between.

### Structural and operational

| Column | Meaning |
|---|---|
| `n_ops` | Total operations in the plan. |
| `n_joins` | Join operations. |
| `n_sel` | Selection and subquery-block operations. |
| `n_agg` | Aggregation operations. |
| `n_sort` | Sort operations, including the extra sorts a sort-merge join needs. |
| `join_typ` | 0 nested loop, 1 hash, 2 sort merge, 3 index nested loop. Categorical — one-hot encode for a linear model. |
| `access` | 0 sequential, 1 index. Categorical. |

### Pipeline and parallelism

| Column | Meaning |
|---|---|
| `n_pipe` | Operations fused into an in-memory pipeline, so their output is never written to storage. |
| `pipe_max` | Longest pipeline, in operations. |
| `n_par` | Operations run on partitioned input. |
| `par_max` | Largest partition count actually achieved. Capped by devices at the tier, so an operation on l3 never exceeds 1. |

### Storage tier

| Column | Meaning |
|---|---|
| `d_0` … `d_3` | Volume read and written on each tier, MB. `d_0` is HDD, `d_3` NVMe. |
| `n_cross` | Operations whose read tier differs from its write tier. |
| `n_push` | Operations whose output goes to a *faster* tier than it was read from. |
| `tier_span` | Slowest tier minus fastest tier the plan touches. |

The tier group is the reason two plans that perform identical operations and
move identical total volume can differ in cost by a quarter or more. If you
collapse `d_0`–`d_3` into one total, that distinction is lost.

### Data movement

| Column | Meaning |
|---|---|
| `read_total` | Total read from persistent storage, MB, including re-reads of intermediates. |
| `write_total` | Total written, MB. Lower than the sum of operation outputs when operations pipeline. |
| `inter_max` | Largest intermediate result, MB. Decides whether an operation can pipeline or sit on a small fast tier. |
| `reduce` | Final output over total input. A property of the query, so **constant across the candidates of one instance** — it separates instances, not candidates within one. |

## Targets

Pick one. Do not feed one target in as a feature for another; in particular
`cost` trivially determines `optimal`.

| Column | Task |
|---|---|
| `best_strategy_tag` | Multiclass: which plan strategy wins for this instance. |
| `optimal` | Binary: is this candidate the cheapest of its instance. |
| `plan_template_id` | The template the framework should retrieve. |
| `cost_ratio_to_best` | Regression: this cost over the best cost, 1.0 for the winner. |
| `cost` | Regression: estimated execution cost in time units. |

## Provenance — deliberately not features

`instance_provenance.csv` records `scale_factor` (SF1, SF3, SF10) and
`placement` (baseline, cold, hot, split). These are how the 180 instances were
produced from 15 queries: three table-size settings and four storage layouts. `baseline` is the deployed
configuration; `cold`, `hot` and `split` are hypothetical variants standing for
the same database after data migration.

They are kept out of the feature tables on purpose. A query arriving at runtime
carries no "scale factor" or "placement" label, so a model trained on them
would not transfer. Everything they affect is already observable through
`input_mb`, `size_class_max`, `n_large`, `n_small`, `tier_min`, `tier_max` and
the per-tier volumes, which is what a real system can actually measure.

Use the provenance file for analysis — for instance, to check whether accuracy
degrades on the `cold` placement — but not for training.

## How to split

Split on `query_group_id`, never at random.

```python
from sklearn.model_selection import GroupKFold
cv = GroupKFold(n_splits=5)
cv.split(X, y, groups=df.query_group_id)
```

Instances of one group share a normal form and therefore have identical
structural features. A random split puts near-identical rows on both sides and
the score becomes meaningless.

## Baselines

Grouped 5-fold, splitting on `query_group_id`.

| Task | Target | kNN (k=5) | Random forest |
|---|---|---|---|
| which strategy wins | `best_strategy_tag` | 0.63 | 0.69 |
| is this the optimal candidate | `optimal`, F1 | 0.55 | 0.60 |
| which query group | `query_group_id`, per instance | — | 1.00 |

The third row is a **sanity check, not a result**. Structural features come
from the normal form, so every instance of a query has identical structural
features by construction and the group is recovered exactly. Report it as
confirming that normalisation does what it claims, not as model performance.

Cost ratios within an instance run 3.0× to 37.5×; an arbitrary candidate costs
2.5× the best. That gap is what a good model recovers.

## What is measured and what is assumed

**Measured:** tier read and write speeds, device counts per tier, and the table
sizes and home tiers of the deployed database. The 15 queries are the TPC-H
benchmark queries.

**Assumed by the generator**, all as named constants at the top of the script:

| Constant | Value | Why it matters |
|---|---|---|
| `CAP` | l2 6000 MB, l3 2000 MB | Decides when a plan can put an intermediate on a fast tier. Device counts are measured; capacities are not. |
| `BUF` | 1024 MB | Transient memory. Controls pipelining and hash-join spilling. |
| `RAND` | 3.0 | Index probes are seek-bound. Without this, index access wins every plan. |
| selectivities | per query | Standard TPC-H estimates for the given constants, not measurements. |
| output ratio | 0.02 | Grouped output as a fraction of grouping input. |

These are the first things to revisit if the costs are ever validated against a
real execution.
